# Clipnest — Adversarial Code Review

Scope: `Sources/ClipnestCore/`, `ClipnestApp/Sources/`, `Tests/ClipnestCoreTests/`, `.github/workflows/release.yml`, `Casks/clipnest.rb`. `ClipnestApp/DerivedData/**` excluded (vendored build output). Reviewed at `HEAD = bc548c0` ("updated release.yml"). Every finding below was checked against the actual source and, where practical, verified by running the real toolchain (`swift build`, `swift test`, `swift format lint --strict`, `xcodebuild`) rather than inferred from reading alone; findings that could not be mechanically verified are marked PLAUSIBLE instead of CONFIRMED.

There is a prior, separate maintainability-focused pass at `docs/review/implementation-review.md` (God-object/DRY/testability angle). This review is the correctness/concurrency/security/process angle requested for this pass; where the two overlap (the SwiftData test-container comments, the `SelectedTextAccessing` force-cast) this report adds new, independently-gathered evidence rather than just repeating the prior write-up.

**Status: partially resolved (see ✅ notes)** — F1 (lint-gate failure) and F2 (test-container churn) were fixed 2026-08-13; the remaining findings (the `SelectedTextAccessing` force-cast, the `Casks/clipnest.rb` `sha256 :no_check` placeholder, etc.) are unchanged and still stand as originally reported.

## Privacy & security

Ran the mandatory security pass (this app captures/persists clipboard content, which is first-class sensitive data per coding-standards.md).

- **No networking anywhere**: grepped `Sources/ClipnestCore` and `ClipnestApp/Sources` for `URLSession`, sockets, and literal `http(s)://` outside of the link-scheme allow-list (`PasteboardReader.validLinkSchemes`) and the release/cask URLs (which are build tooling, not app runtime). Clean.
- **Concealed/transient pasteboard markers**: `PrivacyFilter.shouldCapture` (`Sources/ClipnestCore/Clipboard/PrivacyFilter.swift:52-58`) checks `org.nspasteboard.ConcealedType`/`TransientType` first and unconditionally — no parameter combination bypasses it, and this is well covered by `PrivacyFilterTests.swift` (8 tests, including an explicit "cannot be bypassed even with a non-paused, non-excluded, empty-custom-list call" test). No bypass found.
- **Password-manager exclusion**: built-in bundle-ID list is additive-only with any user-supplied list (`Self.builtInExcludedBundleIDs.union(customExcludedBundleIDs)`), matching the "can only ever add, never remove" requirement.
- **No clipboard content in logs**: every `os.Logger` call site reviewed (`ClipboardMonitor.logCaptureFailure`, `SwiftDataClipStore`/`SwiftDataSnippetStore`'s backfill error logs, `SnippetExpander`'s `findByKeyword` failure log) logs only error type/case names or `String(describing: error)` — never `previewText`, blob bytes, or the read selection text. Confirmed by reading every logger call site in the reviewed files; none interpolate content.
- **No secrets in scripts/workflows**: `release.yml` reads all signing/notarization credentials from GitHub Actions secrets and routes them through `notarytool store-credentials`/a throwaway keychain — no literal Apple ID, password, or API key found in the workflow or `Casks/clipnest.rb`.
- **`NSPasteboard: @retroactive @unchecked Sendable`** (F1's subject): the `@unchecked` claim itself is sound — `NSPasteboard` is documented as a thread-safe distributed-object-backed singleton, and nothing in `Paster`/`ClipboardMonitor` mutates it outside expected read/write call patterns. The finding here is purely the lint-hygiene issue (F1), not a soundness problem.
- **`ClipboardSelectionReplacer`** (`ClipnestApp/Sources/System/ClipboardSelectionReplacer.swift`): borrows the real system pasteboard to synthesize copy/paste for snippet expansion in AX-hostile apps, but correctly suppresses `ClipboardMonitor` capture for the whole transaction (`beginSuppression`/`endSuppression` wrapped in a `defer`, so it's called even on early return) and restores the original clipboard byte-for-byte before resuming capture — verified the defer ordering (restore, then ignore the restore's own changeCount, then resume) is correct and doesn't leak the transient selection/body into history.

**Security verdict: no bypass or leak found in the reviewed range.** F1/F2 are process/hygiene, not security defects.

## Test coverage gaps

- **`ClipnestApp` has zero automated tests** — confirmed via `project.yml` (no `ClipnestAppTests` target defined at all, not just "no test files exist"). This is a known, accepted design tradeoff per coding-standards.md ("UI kept thin by design... light smoke tests only"), but it means every finding in this report that touches App-target code (F1's neighbor context aside — F1 is Core, but F3/`SelectedTextAccessing`, `ClipboardSelectionReplacer`, `PickerViewModel`'s 1,258 lines) has no regression net beyond manual verification and whatever `ClipnestCoreTests` exercises indirectly through mocks.
- **`WindowPlacement.swift`** (pure `CGRect`/`CGPoint` math, zero AppKit dependency per its own doc comment) is the most test-ready file in the App target and has no test at all — already flagged in the prior maintainability review; repeating here because it's the single highest-value, lowest-effort test gap in the tree.
- **F1/F2's own blast radius has no regression test**: nothing in the suite asserts "the store test containers don't leave files on disk" or "`swift format lint --strict` passes" — both are process properties that, by nature, won't be caught by `swift test` itself. Recommend adding the lint step to CI (Medium finding above) as the actual fix rather than trying to unit-test lint cleanliness.
- Core-side coverage is otherwise strong: 176 tests, real edge cases exercised (pagination boundaries, dedup, retention caps, a genuine on-disk Core Data migration reproduction, large-payload substring search). No gaps found in the reviewed files beyond what's listed above.
